#+title: Головний файл

Точка входу застосунку. Це довготривалий процес: клієнт =mcp= (тут — Claude Code) запускає цей бінарник
підпроцесом і спілкується з ним через ~stdin~ / ~stdout~ протягом усієї сесії. Механіку протоколу
розписано нижче; сервер побудовано за зразком ~am-mcp~ (а той — за ~org-tmetric-mcp~).

* Протокол: =json-rpc= над =stdio=

=mcp= (=Model Context Protocol=) — це =json-rpc= 2.0 поверх одного з кількох транспортів; наш — ~stdio~
(локальний процес, а не мережевий сервіс). Кожне повідомлення — окремий рядок тексту без символів нового
рядка всередині. Повідомлення бувають двох видів: запит (~request~, має поле ~id~ й очікує відповідь з
тим самим ~id~) і повідомлення (~notification~, без ~id~, відповіді не буде). Із методів, які треба
обробляти, ~initialize~, ~tools/list~ і ~tools/call~ — запити, а ~notifications/initialized~ —
повідомлення, на яке ми нічого не відповідаємо.

* Підмодулі

~client~ — вхід до Bitwarden/Vaultwarden (побудова клієнта, синхронізація, сейф), див.
[[file:main-client.org][~main-client.org~]]. ~state~ — збереження стану між запусками процесу, див. [[file:state.org][~state.org~]]. ~login~ —
мережевий вхід, рідкісна явна команда, див. [[file:login.org][~login.org~]]. ~unlock~ — локальне розблокування без
мережі, звичайний шлях старту сервера, див. [[file:unlock.org][~unlock.org~]]. ~tools~ — реєстр і диспетчеризація
інструментів, див. [[file:main-tools.org][~main-tools.org~]].

* Довідка (~--help~)

=mcp=-клієнт (Claude Code) передає параметри звичайного старту через змінні середовища, а не через
аргументи командного рядка — окрім самої довідки й команд ~login~/~logout~ (які запускає вручну сам
користувач у терміналі, не =mcp=-клієнт, [[file:login.org][~login.org~]]/[[file:state.org][~state.org~]]). Без перевірки ~--help~ проходив
далі до ~client::connect()~ і провалювався на відсутньому ~BW_SERVER~, показуючи загальну помилку
користувача замість довідки. ~require_url~ — спільна перевірка позиційного аргументу для обох команд.

* Журнал помилки запуску

Клієнт =mcp= (Claude Code) при невдалому `/mcp reconnect` показує лише узагальнене "connection
closed" — детальне повідомлення `connect()` (з ланцюгом `source()`, [[file:main-client.org][~main-client.org~]]) іде
тільки в ~stderr~ і губиться. Тому додатково пишемо його у файл за =XDG_STATE_HOME=
(`~/.local/state/bwm-mcp/last-error.log`, перезаписується щоразу) — після невдалого підключення
досить подивитись цей файл, не перезапускаючи бінарник вручну. Запис — найкраща спроба: якщо каталог
недоступний чи диск заповнений, помилка запису мовчки ігнорується (сам старт і так уже провалюється,
подвоювати відмову нема сенсу). Для ~429~ (вичерпаний rate-limit входу Vaultwarden) додаємо коротку
підказку про `LOGIN_RATELIMIT_MAX_BURST`/`LOGIN_RATELIMIT_SECONDS`.

#+begin_src rust :noweb-ref Визначення
  fn log_startup_error(message: &str) {
      let hint = if message.contains("429") {
          " Це, найімовірніше, rate-limit входу Vaultwarden \
            (LOGIN_RATELIMIT_MAX_BURST/LOGIN_RATELIMIT_SECONDS) — часті реконекти вичерпують ліміт."
      } else {
          ""
      };

      let Ok(home) = std::env::var("HOME") else { return };
      let dir = std::path::Path::new(&home).join(".local/state/bwm-mcp");

      if std::fs::create_dir_all(&dir).is_ok() {
          let _ = std::fs::write(dir.join("last-error.log"), format!("{message}{hint}\n"));
      }
  }
#+end_src

* Модуль

Цикл читає ~stdin~ порядково, поки клієнт не закриє канал (тоді ~next_line~ поверне ~None~ і процес
завершиться) — окремого повідомлення про завершення в =mcp= не передбачено. Клієнт до Bitwarden
з'єднується (й автентифікується) один раз при старті — усі інструменти діляться ним через ~Arc~ (сам
~PasswordManagerClient~ дешево клонується, але ~Arc~ явно підкреслює, що це спільний стан на весь
процес, а не одноразовий). Невдалий вхід (неправильний пароль, недоступний сервер, незадані змінні
середовища) — очікувана помилка користувача, не внутрішній збій, тож без паніки: зрозуміле повідомлення
в ~stderr~ і код виходу ~1~.

#+end_src

* Обробка одного рядка

Порожні рядки пропускаємо. Якщо рядок не розбирається як =json=, за специфікацією відповідаємо помилкою
розбору з ~id: null~ (справжнього ~id~ ми ще не знаємо) і переходимо до наступного рядка. Якщо розібрався
— дістаємо ~id~ (він визначає, запит це чи повідомлення), ~method~ і ~params~.

* Ізоляція від паніки на рівні одного запиту

Код інструментів вільно користується ~unwrap()~ (так простіше діагностувати неочікувану форму відповіді
Bitwarden), але процес живе, поки живе вся сесія: паніка під час одного запиту не повинна вбивати сервер.
Тому диспетчеризацію кожного рядка запускаємо в окремому ~tokio::spawn~: паніка стає ~Err~ від
~JoinHandle~, який перетворюємо на відповідь =json-rpc= з кодом ~-32603~. Для повідомлень (без ~id~)
результат не чекаємо.

#+begin_src rust :noweb-ref Ізоляція-від-паніки
  match id {
      None => {
          tokio::spawn(dispatch(bw.clone(), method, params));
      }
      Some(id) => {
          let outcome = tokio::spawn(dispatch(bw.clone(), method, params)).await;

          let response = match outcome {
              Ok(Ok(result)) => serde_json::json!({ "jsonrpc": "2.0", "id": id, "result": result }),
              Ok(Err((code, message))) =>
                  serde_json::json!({ "jsonrpc": "2.0", "id": id, "error": { "code": code, "message": message } }),
              Err(_panic) => serde_json::json!({
                  "jsonrpc": "2.0",
                  "id": id,
                  "error": { "code": -32603, "message": "Внутрішня помилка сервера під час обробки запиту." },
              }),
          };

          write_response(&mut stdout, &response).await;
      }
  }
#+end_src

* Диспетчеризація методу

~Err~ тут означає лише помилку рівня протоколу (метод, якого ми не підтримуємо) — код ~-32601~. Помилки
самого інструмента (наприклад, елемент не знайдено) — не помилка протоколу: ~tools/call~ завжди повертає
~Ok~, а невдачу передає полем ~isError: true~ у результаті, тож клієнт і модель бачать причину, а не
обрив з'єднання.

#+begin_src rust :noweb-ref Визначення
  async fn dispatch(bw: Arc<client::Bw>, method: String, params: serde_json::Value) -> Result<serde_json::Value, (i64, String)> {
      match method.as_str() {
          "initialize" => Ok(serde_json::json!({
              "protocolVersion": params["protocolVersion"].as_str().unwrap_or("2024-11-05"),
              "capabilities": { "tools": {} },
              "serverInfo": { "name": "bwm-mcp", "version": env!("CARGO_PKG_VERSION") },
          })),
          "notifications/initialized" | "ping" => Ok(serde_json::json!({})),
          "tools/list" => Ok(serde_json::json!({ "tools": tools::list() })),
          "tools/call" => {
              let name = params["name"].as_str().unwrap();
              let arguments = params.get("arguments").cloned().unwrap_or(serde_json::json!({}));
              Ok(tools::call(&bw, name, &arguments).await)
          }
          _ => Err((-32601, format!("Метод не підтримується: {}", method))),
      }
  }
#+end_src

~initialize~ повертає той самий ~protocolVersion~, що надіслав клієнт (чи запасне значення, якщо його
немає), і оголошує єдину можливість — ~tools~.

* Запис відповіді

Коли ~stdout~ з'єднаний з каналом, він буферизується блоками, а не порядково: без явного ~flush~
відповідь може осісти в буфері й ніколи не дійти до клієнта. Тому кожен запис супроводжуємо ~flush~.

#+begin_src rust :noweb-ref Визначення
  async fn write_response(stdout: &mut tokio::io::Stdout, response: &serde_json::Value) {
      let text = serde_json::to_string(response).unwrap();
      stdout.write_all(text.as_bytes()).await.unwrap();
      stdout.write_all(b"\n").await.unwrap();
      stdout.flush().await.unwrap();
  }
#+end_src
